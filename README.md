# training-log

筋肥大を目的とするトレーニング記録PWA。**記録専用。**分析・推定1RM・回復判定（層2）は
Obsidian Vault 側（`projects/training/`）で行うため、このアプリには入れない。

設計の根拠は Vault の [`projects/training/記録項目は落とす側で決まった.md`] にある。

## 記録するもの

セット単位（1セット = 1レコード）:

| 項目 | 備考 |
|---|---|
| 種目ID | 種目マスタ参照。文字列ではない |
| 重量 (kg) | |
| レップ | |
| RIR | 0/1/2/3/4+ の5値。**全セット必須** |
| 完了時刻 | 記録ボタンを押した瞬間。レストはここから導出する |

日単位で **体重**（測定時刻つき）。種目マスタは **名前 + 動作パターンID（16枠）**。

## 意図的に持たない列

`器具タイプ`（実測で群間差2ptに対し群内6倍、説明変数として無価値） /
`部位`（動作パターンIDから導出できる） / `RPE`（RIRと同じ情報） /
`レスト時間`（完了時刻の差から導出） / `睡眠・体調・食事` /
`ウォームアップフラグ`（ウォームアップを行わないため）

## 動作パターンは16枠で固定

種目は自由に増やせるが、作成時に16パターンのどれかへの紐付けが必須。
判定器はパターン単位で集計するため、**枠を増やすとデータが薄まって判定が死ぬ。**
121種目に散って1種目11セッションしか溜まらなかったのが既存アプリの失敗だった。

`patterns.js` を参照。Legの5枠目だけは元の分類器のフォールバック `"その他"` を
`下腿（カーフ）` に置き換えてある（設計判断であって実測ではない）。

## データ

IndexedDB (`training-log`)。**追記のみ。**セットの取り消しは物理削除ではなく
`voidedAt` を立てるだけ。同期を後から足すとき追記のみなら競合しないため。

**同期は未実装。**現状は端末内に溜まるだけで、ヘッダの「書き出し」から JSONL を
取り出す。Vault の JSONL へ流す経路は、全セットRIR入力が継続すると分かってから決める。

## 動かす

ES モジュールを使うので `file://` では動かない。サーバが要る。

```sh
cd ~/Workspace/projects/training-log
python3 -m http.server 8777
```

- Mac で確認: <http://localhost:8777/>
- iPhone から: `http://<MacのLAN IP>:8777/` を Safari で開き、共有 → ホーム画面に追加

**注意: `http://` ではオフラインが効かない。**Service Worker は secure context
（`https://` か `localhost`）でしか登録できないため、LAN の平文HTTPでは
`sw.js` が無視される。ジムに電波がない場合、実運用には HTTPS 配信が要る。
