# training-log

筋肥大向けトレーニング記録アプリ。**記録専用。**分析は Obsidian Vault 側（`projects/training/`）で行う。

```
ジム（このPWA）  記録のみ。IndexedDB に追記で溜める
      ↓  ship() … 現在は手動エクスポート（共有シート）
Vault内 JSONL（追記のみ）
      ↓
Mac（Vault / Claudian + DuckDB）  1RM計算・MAD・回復判定
```

## 画面

下部タブは**2枚だけ**。**起動時は必ず「記録」から開く**（タブ位置を復元しない）。
分ける理由は使用文脈で、入力はジムで片手・数秒、閲覧は家で両手・数分。

| タブ | 中身 |
|---|---|
| 記録 | 入力面。**前回のセットを常時表示**し、RIRのタップで保存。右にフォーカス指標。下に今日のワークアウト全体 |
| 履歴 | 日付（セッション一覧）/ 種目（PR・推移・全履歴）/ 体重 の3つの切り口。搬出もここ |

**体重をトップレベルに置かない**のは実アプリに合わせた判断である。Hevy は
Profile → Measures の2階層下に体重・体脂肪・周囲径をまとめており、Strong では
身体測定がそもそも有料機能で無料版に存在しない。タブを1枚割くと、どの既存
アプリよりも体重を前に出すことになる。

一般の Workout / History / Exercises / Measure / Profile からは Profile
（1人用で共有先がない）と Exercises（記録面のピッカーで足りる）を落とした。

**セッションはオブジェクトとして持たない。**開始・終了・所要は `by_day` の
最初と最後の `at` から導出する。Hevy / Strong が明示オブジェクトを持つのは
セッション中にストップウォッチが走り、一時停止・再開・時間の手修正ができる
ためで、RIRタップで即確定するこの設計には進行中状態が存在しない。

**推定1RMは出さない。**自己記録は最大重量・単セット最大挙上量・1日の最大
挙上量の3つで、すべて実測値の算術。Strong は Brzycki 式で推定1RMを出して
チャートにするが、モデル依存の推定をアプリに焼くと数値の来歴が切れる。
推定は Vault 側でやる。

## フォーカス指標

Strong が種目の右上に置いているものの移植。タップで巡回する。

総挙上量 → 前回比（前回セッションの挙上量に対する%） → 総レップ → 最高重量

4つとも既存の列からの導出で、**保存する列は増えない。**選択はUIの好みであって
訓練データではないので `localStorage` に置き、IndexedDB には入れない。

## 休憩ストップウォッチ

**カウントダウンではなく計上。開始は手で押す。**目標時間を持たないので
鳴らすものも ±30 も無い。

**休憩は「セットとセットに挟まれた区間」としてしか記録しない。**

```
セット1を保存 ──▶ 錨を置くだけ。**時計は動かさない**
開始を押す    ──▶ ここから測る
終了を押す    ──▶ 止めるだけ（止めた時刻が endedAt。まだ書かない）
セット2を保存 ──▶ ここで初めて1件書く { from: セット1, to: セット2 }
                 そしてセット2を次の錨にする
```

帯は4状態しか持たない。

| 状態 | 表示 | ボタン |
|---|---|---|
| 錨なし | 休憩 — セットを記録すると測れる | なし |
| 待機 | 休憩 0:00 | 開始 |
| 計測中 | 休憩 m:ss ・中央値 m:ss | 終了 |
| 停止中 | 休憩 m:ss ・次のセットで記録 | 開始 / ✕ |

- **開始を一度も押さなければ何も記録されない。**測っていないものは書かない
- 終了を押し忘れても、次のセットが区間を閉じる
- ✕ は計測だけ捨てる。**錨は残る**のでもう一度 開始 を押せる
- 1秒未満は誤爆として捨てる
- その日の最初のセットより前は錨が無いので測れない

経過は「開始時刻からの引き算」で出す。カウンタを足していく実装だと
バックグラウンドで絞られた分だけ狂うが、開始時刻を持っていれば復帰した
瞬間に正しい経過が出る。`visibilitychange` で引き直している。

参照としてその種目の**実測レストの中央値**を帯に出す（同日・同種目の連続セット
間隔の中央値、15秒刻み）。目標ではないので超えても止まらず色が変わるだけ。

### ここだけ列を足した

`rests` ストアを新設し、DB を **v2** に上げた（既存の v1 は `oldVersion` で
分岐して作り足すだけ。`sets` のスキーマは触っていない）。

```
rests: { ulid, fromSetUlid, toSetUlid, startedAt, endedAt, day }
索引: by_day / by_to（一意。1つのセットに2つの休憩を紐づけない）
```

種目は `fromSetUlid` から引けるので列に持たない。

`projects/training/記録項目は落とす側で決まった` は「レスト時間は持たず
`at` の差から導出する」と決めていた。**ここはその決定を覆している。**根拠は
導出で代用できないこと: `at` の差は「前のセットを終えてから次のセットを終える
まで」なのでセットの実行時間が混ざり、常に計測値より長い。測っているものが違う。

導出値も消していない。UIは**計測値があればそれを `休 m:ss` で、無ければ
従来の導出値を `休N分` で出す。**書式が違うのでどちらを見ているか分かる。
突き合わせは `toSetUlid` の完全一致で、時刻の近さから推測していない。

搬出JSONLには `type: "rest"` の行として乗る。

## 過去セットの訂正## 過去セットの訂正## 過去セットの訂正

**列を1つも足していない。**訂正は「元の行を `voidedAt` で倒し、同じ `at` で
新しい行を追記する」。`supersedes` 列を持たせる案は捨てた — Vault 側は
すでに `voidedAt` を見て間引くので、追加の解釈規則が要らない。

訂正行の ULID は **現在時刻**で振る（`at` ではなく）。ULID の辞書順が表すのは
追記順であり、訂正は今おこなわれた追記だから。イベント時刻は `at` が持つ。

体重の行は倒せない（`bodyweight` に void 列がない）。訂正は同じ日に正しい
値を入れ直す。その日の代表値は**最後の入力**を使う。

## 種目プリセット

`src/lib/presets.ts` に43件。**起動時に黙って入る**（ボタンは出さない）。
同名が既にあるものは飛ばすので、何度起動しても増えない。

選定基準は「研究でよく使われる」。具体的には下の2本のレビューの、採用研究の
トレーニングプロトコルに **実際に名前が出ている種目だけ** を採った。

- Superset Versus Traditional Resistance Training Prescriptions (PMC12011898)
- Comparison of Traditional and Advanced Resistance Training Paradigms (PMC11022786)

ヒップスラスト（臀筋肥大SR/MA, PMC12018462）とノルディックハムストリングカール
（medRxiv 2024）の2件だけ出典が別。

**懸垂とブルガリアンスクワットは意図的に入れていない。**定番ではあるが上の
レビューの種目リストに現れなかった。基準に厳密に従った結果で、良い種目では
ないという判断ではない。

43件は16枠すべてを埋める。種目を増やしても**回復判定は16枠で集計するので
薄まらない**（`patternId` が必須のため）。薄まるのは種目タブ側の個別履歴だけ。

## 種目ピッカー

43件を平坦に並べない。**部位 → パターン → 種目の木**にしてある。

- 部位はアコーディオンで、開くのは1つだけ
- 木の一番上に「最近使った」枝（直近8件）。ジムでの最短経路を階層に潰させない
- **検索中は木を畳んで平坦な結果を出す。**検索しているときに階層を辿らせるのは
  手数が増えるだけなので

## 記録する列

セット単位で `種目ID / 重量 / レップ / RIR / 完了時刻` の4列（+種目参照）、日単位で体重。
器具タイプ・部位・RPE・レスト・体調は意図的に持たない。根拠は Vault の
`projects/training/記録項目は落とす側で決まった`。

## 配信

**https://ben1san.github.io/training-log/**

`master` への push で GitHub Actions が `npm ci → check → build` して Pages へ出す
（`.github/workflows/pages.yml`）。

配信先を固定しているのは **IndexedDB がオリジン単位**だからである。URLが変われば
記録は丸ごと消えるので、使い捨てのトンネルURLは使えない。

`base: './'` のまま。サブパス配信でも SW のスコープ・manifest の `start_url` /
`scope` / アイコンがすべて `/training-log/` に解決し、オフライン再読み込みも
通ることを確認済み。

**オリジンは `ben1san.github.io` であってパスではない。**同じユーザーの他の
Pages プロジェクトとストレージ名前空間を共有するので、DB名 `training` は
その範囲で一意である必要がある。

**iPhoneではSafariで開いてホーム画面に追加して使う。**Safariはスクリプト
書き込みストレージを7日間の未使用で破棄し、インストール済みPWAだけが対象外
（この前提は未検証）。インストールされていない状態では画面上部に警告が出る。

## 旧実装から引き継いだ決定

2026-09-03 の vanilla JS 実装を置き換えたもの（履歴の最初のコミットに残してある）。
そのとき決めていて、今回そのまま持ってきたものが2つある。

- **動作パターン16枠のIDと名称。**Leg の5枠目は元の分類器のフォールバック `"その他"` を
  `下腿（カーフ）` に置き換えたもので、実測ではなく設計判断である
- **追記のみ。セットは物理削除しない。**取り消しは `voidedAt` を立てるだけで行は残る。
  同期を後から足すとき、追記のみなら競合しないため

**IndexedDB の名前は `training-log` ではなく `training` にしてある。**旧実装の
`training-log` DB はスキーマが違うので、同名にすると旧データを壊す。旧DBはそのまま
残っているので、中に記録があるなら移行は別途やる。

## 同期経路は未決
